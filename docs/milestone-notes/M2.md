# M2: Board-independent logic with host tests (2026-10-11)

- **Done:**
  - Contract **0.2.0** (additive, no wire change; `contracts/CHANGELOG.md`): protocol.md §5-§7 now pin
    down what 0.1.0 left open: per-connection transfer handles, journal/resume rules, `XFER_BEGIN`
    check order, chunk/FINISH rules, config/app semantics and paging, notification filters and
    storage. New `contracts/test-vectors/transfer.json` (27 scenarios, 246 steps, app+board),
    generated from scripted client steps by the Python reference board model
    `tools/epager_proto/transfer.py`; every step declares its expected statuses.
  - `components/config_store`: `kv_storage` interface + `kv_mem` fake; typed config from the
    generated registry tables, CONFIG_SET batch semantics (unknown keys skipped and reported,
    all-or-nothing, `expected_revision`, 64-entry limit, no-op writes keep the revision), reset,
    policy revision bump, change callback, defaults and migration by `since`; message adapter for
    CONFIG_GET/SET/RESET and TIME_SYNC.
  - `components/notification_pipeline`: ANCS/Android → NotificationEvent (text normalised and
    truncated on the board, enum fallbacks, ANCS priority precedence, ANCS date → UTC), filters
    (app policy, category mask, minimum priority, show_silent, quiet hours across midnight, unset
    clock), RAM store with add/modify/remove events and eviction (oldest hidden first), ANCS session
    reset, seen apps (LRU except explicit policies, persisted per slot, recency flushed lazily);
    message adapter for NOTIF_* and APPS_*.
  - `components/transfer`: state machine for XFER_*, STORAGE_INFO, ASSET_LIST, ASSET_DELETE;
    `blob_storage` + `blob_mem`, `xfer_fw_sink_t` + `fw_mem`; resume journal; windowed acks; prefix
    CRC-32; SHA-256 + CRC-32 over the stored bytes at FINISH; asset container check
    (asset-formats.md, stable parts); atomic install (temp + rename); boot cleanup of orphans.
    `xfer_ota`: semver precedence and downgrade refusal, battery gate (Paper 30 %, skipped without
    a reader, refused if the reader fails), progress events, pending-verify / self-check / timeout /
    rollback states with a persisted pending-update record.
  - `protocol`: portable SHA-256 (D24), `proto_w_response()`; `gen.py` emits the config key count,
    string max length and per-key `since` (registry unchanged).
  - Tools: `tools/coverage.py` (gcov JSON, no gcovr), `tools/xtensa_check.sh`.
- **Verified (how):**
  - `ctest --test-dir build/host`: 6/6 executables pass under ASan+UBSan (test_vectors 12,
    test_unit 14, test_config 20, test_pipeline 20, test_transfer 24, test_fuzz 7 Unity tests).
  - transfer.json: all 27 scenarios replayed **byte-for-byte** by the C code (test_vectors) and by a
    fresh Python model (pytest). The runner was shown to fail on three deliberate C mutations
    (ack window, NO_SPACE accounting, journal interval: 17, 1 and 2 failing scenarios); the
    pipeline tests caught three deliberate mutations as well.
  - Acceptance list: quiet hours across midnight and with time zones (table test); config invalid /
    out-of-range / unknown keys and partial-batch rejection; transfer happy path, resume after
    disconnect and after reboot, bad offset, oversize/no space, CRC and SHA mismatch, abort (vectors);
    power loss swept over every storage write of an asset replacement (17 cut points: the installed
    asset is always exactly the old or the new file, never a mix, and the transfer resumes with a
    matching prefix CRC) and of a firmware transfer (29 cut points); OTA refusals for low battery and
    same/older/missing/invalid versions; OTA boot states.
  - Fuzzing (ASan/UBSan, 1,000,000 iterations, clean): mutated storage records (config, seen app,
    journal, OTA record); mutated requests through every handler (every reply must parse as a valid
    message within the channel limit); random transfer sequences with power cuts and reboots. The
    sequence fuzzer **found a real bug**: if deleting a stale temp file failed during a fresh
    XFER_BEGIN, a shorter new file could pass verification and be installed with the old tail. Fixed
    (BEGIN answers INTERNAL; FINISH requires exactly `size` stored bytes) with a regression test.
  - Line coverage of the portable core (gcov, `tools/coverage.py`, fuzz targets included):
    **98.2 %** (2209/2250 lines); lowest file `proto_config.c` 78 %.
  - `pytest tools`: 177 pass; `contract_check.py` OK (now also validates every transfer.json message
    against the schemas).
  - xtensa-esp32s3-elf-gcc 14.2, `-Os -Wall -Wextra -Werror -Wpedantic -Wshadow -Wstrict-prototypes`:
    no warnings. Code: protocol 17.6 KB (10.8 KB generated tables), config_store 3.3 KB,
    notification_pipeline 4.9 KB, transfer 7.8 KB (1.3 KB of it fakes the linker drops). Largest
    stack chain: CONFIG_SET handling about 2.6 KB.
- **Not verified:** everything on hardware. Assumed from documentation and to check in M4/M6: NVS
  `set` is atomic per key, LittleFS rename is atomic and `flush` makes data durable, `esp_ota_resume`
  continues a partial image. Not done: SHA-256 speed on the S3 (D24), the Dart app running
  transfer.json, LittleFS component availability (moved to M4), a real clock or CTS time source.
- **Decisions / contract changes:** contract 0.2.0 (above); D24 portable SHA-256; D25 interface and
  fake placement (`xfer_ota` in `transfer`); D26 storage records (non-default config values, lazy
  seen-app recency, journal timing); D27 re-read verification at FINISH.
- **Follow-ups for M3/M4:** M3 builds the core dispatcher (route channels to `cfg_handle`,
  `npipe_handle`, `xfer_handle`; PING, ERROR, status-only replies for invalid requests,
  DEVICE_STATUS, CONFIG_CHANGED/APP_SEEN encoding, `npipe_apps_flush` timer, `xfer_on_disconnect`).
  RAM: the notification store is 1,776 B per slot (88.8 KB for 50) and seen apps 148 B each (18.9 KB
  for 128), so put both in PSRAM. Give the core task at least 4 KB of stack. Pick the board's
  `journal_every` (e.g. 16 KiB) and `max_chunk` from the negotiated MTU.
